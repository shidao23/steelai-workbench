## 2026-09-25 · T86 phase 5 (independent single-point process per temperature; batch path demoted to diagnostic)

- **Route chosen by the project owner.** The formal path is now **one independent process per temperature point**. The 12 components, the fixed phase set, the temperature grid and every scientific restriction are unchanged, and the phase-4 batch warm-start path is kept **only as diagnostic evidence**. T86 **stays `Blocked`**; `pilot_ready_pending_scientific_review` is **not** claimed.
- **New versioned mode** `solver_mode=independent_single_point_process_v1` (`config/calphad_reduced_system_v1.0.json` → `solver_modes`, `status=formal_pilot`). Every point: same normalised composition, the same 12 components plus `VA`, the same fixed phase set, the same pressure/database SHA-256/pycalphad version/config, a **fresh worker process** that recreates `Database`, model and `Workspace`, exactly one temperature solved, then exit before the next point. Points run **strictly serial** (the worker rejects a multi-temperature request with `CALPHAD-WORKER-MODE-001`, and a test asserts a maximum concurrency of one). `batch_workspace_warm_start` is marked `diagnostic_only` / `formal_pilot=false`.
- **Scientific inputs are frozen by policy.** The `forbidden` list forbids deleting a failing temperature, changing the step, interpolating, smoothing, dynamically dropping components or phases, changing `pdens` in response to results, cherry-picking a plausible-looking attempt, and warm-starting from the previous point. Every point differs from the others only in temperature (a test compares the requests field by field).
- **Retry rules.** Formal acceptance requires every point to succeed on its **first** independent process call. One diagnostic retry is allowed but the first failure is still recorded as a failure; a successful retry never changes the formal result and is never spliced into the formal curve (a dedicated test asserts `points == []` with `first_attempt_success=false` and `diagnostic_retry_succeeded=true`).
- **Point contract.** Each point records `request_hash`, temperature °C/K, components, phases, `va_present`, database SHA-256, worker PID and exit code, solve status, active phases and mole fractions, phase-fraction sum, runtime, a sanitized stderr summary, `first_attempt_success` and `solver_mode`; the run carries `point_manifest` and `manifest_digest`. The parent merges only first-attempt successes that pass contract validation, and **a missing point yields no partial curve** (`partial_curve_returned=false`, `points=[]`, `curve=[]`) with the failing points listed.
- **Verification.** New heavy acceptance script `scripts/calphad_phase5_acceptance.py` runs the full 54-point scan for B-DQ and R-DQ three times each (324 independent points) plus a batch-versus-independent comparison on R-DQ, writing a machine-readable report to the git-ignored `outputs/`. The targeted unit tests never start a heavy solver: they use a single-point worker double.
- **Acceptance result: `blocked`.** Of the **324 independent points, 320 succeeded on the first independent process call (98.77 %)**. The four failures were all B-DQ at **875 °C and 900 °C** (two in run 1, two in run 3), and the diagnostic retry failed there too; there were **zero** native aborts, `MemoryError`s and timeouts. R-DQ succeeded 54/54 in all three runs with a three-run maximum absolute difference of **1.3×10⁻⁹** (tolerance 1e-7). The independent mode did **not** remove the failure, which corrects the phase-4 conclusion that warm-starting was the cause: repeating the *same single-point* condition in **fresh processes** succeeded for B-DQ 900 °C only **1 of 8** times and 875 °C **2 of 4** times, failing with "no phase moles". The system is therefore **non-deterministic near the α/γ boundary** in pycalphad 0.11.2 on this host, independently of the solver mode.
- **Second blocking finding — the two solver modes disagree.** On R-DQ, 54 commonly converged points were compared between the batch mode and the independent mode: **one point (675 °C) differs by 1.069×10⁻⁴**, far above the 1e-7 tolerance. Both modes find the same BCC_A2+CEMENTITE+FCC_A1 assemblage but different fractions (BCC_A2 0.9687085569 vs 0.9686500344). Per the rule that one curve must not be chosen over the other, **neither curve is published** and the difference is reported.
- **Also verified and passing:** B/R use identical components, phase set, temperature grid, profiles and solver mode (evaluated at the request level); the physical plausibility guards pass for both heats; the export limitation checks pass (Markdown, CSV and record, with the profile and solver mode on every CSV row). ## 2026-09-18 · T84 round 2 contract correction (handler exception boundary and outcome invariants)

- **Gap 1 - the handler exception boundary.** A handler raising `DomainError` used to be re-raised out of the worker, which aborted `run_once`/`run_batch`, leaked the original `code`, `message` and `details` (a fake connection string, password, host, Windows path and token in the test), and left the job stuck in `leased` with no recorded outcome. `JobWorker._run_handler` now treats **every** `Exception` other than `JobHandlerError` - `DomainError` included - as an unclassified handler failure and converts it to `JobHandlerError(ENT-WORKER-EXECUTION-001, retryable=True)`. A handler domain error therefore never escapes the worker, never interrupts the rest of the batch, never leaves a lease behind, and never exposes its text: the job is recorded as `retrying` (or terminally `failed` once the attempt budget is spent) with the fixed safe code. `BaseException` such as `KeyboardInterrupt` or `SystemExit` is **not** swallowed, so an operator signal still reaches the caller and the lease is left to expiry recovery. The fix sits at the handler execution boundary: `run_batch` has no blanket `except`, and repository claim failures and illegal configuration still propagate (both covered by tests).
- **Gap 2 - complete `JobOutcome` invariants.** An outcome could previously report a status without the persisted fields that go with it. `JobOutcome.__post_init__` now enforces a full status table: `succeeded` requires `state == 'succeeded'`, `attempts == attempt` and no error code; `retry_scheduled` requires `state == 'retrying'`, `attempts == attempt + 1` and an error code; `failed_terminal` requires `state == 'failed'`, `attempts == attempt` and an error code; both `success_unrecorded` and `failure_unrecorded` require `state is None`, `attempts is None` and an error code. Any other combination - including a boolean, negative or string `attempts` counter - fails closed with `ENT-WORKER-CONFIG-001`, so an outcome can no longer claim a persisted state it does not describe, forget the failure code of a known failure, or invent persisted fields for an unknown one. A table-driven test covers 19 contradictory combinations and a further test drives all five real worker paths to prove the invariants hold end to end.

- Transaction boundary: one unit of work owns one connection and one transaction shared by all five repositories, a commit applies every write atomically, an exception leaving the block always rolls back, and any repository handle kept past the boundary fails closed with `ENT-UOW-001`. `committed` is that unit of work's own permanent outcome flag.
